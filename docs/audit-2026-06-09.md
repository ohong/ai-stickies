## 1. Executive Summary

**Health grade: C-.** The architecture is genuinely good for an MVP — clean service layer, a provider abstraction that already anticipates a model router, 144 passing unit tests — but `main` does not compile, there is no CI to catch that, and the payments path can take a customer's money without granting credits. The last five commits are workstream merges (WS1–WS5) that were never built together; the breakage is merge debris, not rot.

**Top 3 risks:**
1. **`main` is unbuildable** — `next build` fails on a type error in the platform-export route, plus a duplicate-key merge artifact in the database types. Nothing merged since WS5 can deploy.
2. **Stripe webhook marks purchases `completed` before granting credits** — if the credit grant fails, the idempotency guard permanently blocks retries. Paid, no credits, no recovery path. Credit mutations are also non-atomic read-modify-write.
3. **User selfies live in a public storage bucket** — anyone with the URL can fetch face photos.

**Top 3 opportunities:**
1. **Model registry as data** — the existing `provider.ts` abstraction is one refactor away from the "switch models with one env var" goal, including Nano Banana Pro and GPT Image.
2. **Async pack generation** — the entire multi-minute pack build runs inside one browser-held HTTP request with fake progress UI; the DB schema and a (currently dead) progress function already support doing it right. This is also the single biggest mobile-UX fix.
3. **Default-first create flow** — collapse the upfront decisions (style text, context text, language picker) into smart defaults with progressive disclosure.

## 2. Repo Map (Phase 1)

**Purpose.** Consumer web app: upload a selfie → AI generates 5 style previews → user picks styles → app generates 10-sticker packs → download/export for LINE, WhatsApp, Telegram, iMessage. Monetized via Stripe credit packs. Maturity: late MVP, solo developer, deployed on Vercel, recently neglected (last commits ~March 2026 as five parallel workstream merges).

**Stack.** Next.js 16.1 (App Router, Turbopack) · React 19 · TypeScript 5.9 · Tailwind 4 · Supabase (Postgres + Storage, publishable/secret key format) · Stripe · Sharp · Bun · Vitest (144 unit tests) + Playwright (5 e2e specs) · Vercel.

**Architecture spine.**
```
app/create (upload + optional customization)
  → POST /api/upload                  (signed-URL upload to Supabase)
  → POST /api/generate/previews       (5 styles in parallel, ref image, sync)
app/create/styles (pick 1–5 styles)
  → POST /api/generate/packs          (N packs × 10 stickers, sync, browser waits)
app/create/results (fetch + download/export/share)
```
Business logic lives in `src/lib/services/*` (good separation); AI providers in `src/lib/ai/` (`provider.ts` routes between `flux.ts` and `fal.ts`; `fireworks.ts` does LLM prompt generation); centralized env config in `src/lib/config.ts`.

**Key directories.**
| Path | Role |
|---|---|
| `app/` | Routes + page-level components (`app/components/`) |
| `src/lib/services/` | Generation, packs, prompts, uploads, credits, sharing, export |
| `src/lib/ai/` | Provider adapters + router (`provider.ts`) |
| `src/components/`, `components/ui/` | Feature components / shadcn primitives (3 component roots total) |
| `src/constants/` | Styles, emotions, platform specs as data (good) |
| `supabase/migrations/` | 3 migrations (auth/RLS, credits, sharing) |
| `my-video/`, `trailer/`, `hero-section-sticker/`, `ai-stickies-demo/` | ~300 files of unrelated Remotion/demo side-projects vendored into the repo |

**Surprises found during mapping.**
- The repo tracks **~40MB**, including a 9.4MB demo .mp4 and 5.7MB .gif at root, plus three embedded side-projects with their own lockfiles.
- Both `bun.lock` **and** `package-lock.json` are tracked (AGENTS.md says Bun).
- No `.github/` directory — zero CI.
- `node_modules` was absent entirely; the project hadn't been installed on this machine since the merges.

## 3. Audit Report (Phase 2)

Each finding: **(a)** what, **(b)** where, **(c)** consequence, **(d)** severity. Facts cite lines; judgments are labeled *[judgment]*.

### 3.1 Correctness & build

**F1 — `main` does not build. (Critical)**
`bun run build` fails: `Buffer<ArrayBufferLike>` is not assignable to `BodyInit` at `app/api/packs/[packId]/export/[platform]/route.ts:112`. Verified by running the build (exit non-zero). Additionally `tsc` reports a duplicate `profiles` key in the `Database` interface at `src/types/database.ts:127` and `src/types/database.ts:179` — WS1 and WS3 each added it; the second silently shadows the first. Consequence: no deploy from `main` is possible; every feature merged in WS4/WS5 is dark. Introduced in `e1287e9` (WS5 export) and the WS1/WS3 merge respectively.

**F2 — Stripe webhook can take money without granting credits. (Critical)**
`app/api/stripe/webhook/route.ts:56-67`: the purchase row is set to `status: 'completed'` *before* `addCredits()` runs. If `addCredits` throws (it's a network call to Supabase), the handler returns 500, Stripe retries, and the retry hits the idempotency check at `route.ts:50-53` (`if (purchase.status === 'completed') return`) and reports success. The customer paid; credits are never granted; no automated recovery. Compounding it, `addCredits` and `deductCredit` are non-atomic read-then-write (`src/lib/services/credits.service.ts:43-73` and `:78-103`) — two concurrent webhook deliveries or generations can lose updates.

**F3 — Pack stickers never see the user's selfie. (High)**
`src/lib/services/pack.service.ts:281-283` calls `generateImageWithFallback({ prompt: prompt.fullPrompt })` with **no `referenceImage`**. The "character description" fed into prompts is the user's *optional* style text (`app/api/generate/packs/route.ts:186`: `style_description ?? ''`). So previews resemble the user (reference image is passed in `generation.service.ts:169-176`), but the final 10-sticker packs are generic text-to-image with at best a textual hint. *[judgment]* This quietly breaks the product's core promise ("turn any selfie into personalized stickers") at the exact moment the user spends a credit. May be a deliberate cost tradeoff, but nothing in code or docs says so.

**F4 — Credit deduction happens after generation, and failures are swallowed. (High)**
`app/api/generate/packs/route.ts:224-235`: credits are deducted per pack *after* packs are built; on `deductCredit` failure the code logs and `break`s — packs are delivered free. The pre-check at `:126` only verifies `balance > 0`, but a user with 1 credit can request 5 packs (`selectedStyleIds` length is checked only against session generations at `:109`, not against credit balance). Combined with F2's race, paying customers and free packs can both happen.

**F5 — Empty catch hides auth failures with a stale excuse. (Medium)**
`app/api/generate/packs/route.ts:137-139`: `catch { /* Auth not available (WS1 not merged yet) */ }`. WS1 *is* merged. Any real error in `createClient()`/`getUser()` (misconfigured env, Supabase outage) silently downgrades a logged-in user to anonymous, skipping the credit check entirely. Violates fail-noisily.

**F6 — `requireEnv` returns `''` in production. (Medium)**
`src/lib/config.ts:16-19`: missing required env vars in production produce a `console.warn` and empty string. A misdeployed app runs with blank Supabase URL/keys and fails far from the cause. *[judgment]* The dev-mode throw is right; production should fail harder, not softer.

### 3.2 Security

**F7 — Selfies in a public bucket. (High)**
`scripts/setup-supabase.ts:31-35` creates the `uploads` bucket with `public: true`; `scripts/fix-uploads-bucket.ts:23-38` exists specifically to force it public so previews load. Face photos are PII; anyone with a URL (`{sessionId}/{filename}`, leaked via logs, referrer, or shared screenshots) can fetch them, and there is no expiry/cleanup actually running (see F13). The `stickers` bucket being public is more defensible (outputs are meant to be shared).

**F8 — Anonymous rate limiting is cookie-deep. (Medium)**
Free-generation limits live on the session row keyed by an httpOnly cookie (`src/lib/services/session.service.ts:134-152`); clearing cookies mints a new session with 10 fresh generations (`session.service.ts:94-111`). Each preview run = 5 paid model calls + LLM calls. `incrementGenerationCount` is also read-then-write racy (`session.service.ts:158-182`), and the previews route increments *in parallel* with generation (`app/api/generate/previews/route.ts:94-105`) rather than reserving first. Consequence: unbounded inference spend for anyone mildly motivated. *[judgment]* Acceptable for launch-stage; worth an IP-based or fingerprint backstop before any paid marketing.

Positive: Stripe signature verification is correct (`webhook/route.ts:24`), upload validation enforces MIME/size server-side (`upload.service.ts:48-60`), storage paths are session-scoped and checked (`upload.service.ts:271`), ownership is verified on results fetch (`app/api/generations/[generationId]/results/route.ts:93-106`), and no secrets are tracked (`.env.local` is gitignored; only `.env.example` is committed).

### 3.3 Architecture & the model-router goal

**F9 — The provider layer is two hardwired branches, not a router. (Medium today; the central theme)**
`src/lib/ai/provider.ts:10` (`type ImageProvider = 'flux' | 'fal'`), if/else dispatch at `:86-89`, duplicated availability/retry/error scaffolding across `flux.ts` and `fal.ts`, and the union duplicated again in `src/types/database.ts:4`. Adding Nano Banana Pro and GPT Image today means editing ≥5 files and widening two union types. Also a leaky abstraction: `fal.ts:101-114` injects sticker-prompt policy ("Create a LINE sticker…") inside the transport adapter, so prompts differ per provider invisibly — switching providers silently changes outputs beyond the model itself. The selection logic (`getDefaultProvider`, `provider.ts:42-58`) hides "prefer fal" in code rather than config.

**F10 — Whole pack generation runs in one synchronous, browser-held request. (High)**
`app/create/styles/page.tsx:82-97` awaits `POST /api/generate/packs` for the full duration; the route builds up to 5 packs × 10 images inline (`packs/route.ts:179-192`). No route exports `maxDuration` (verified by grep across `app/`). Consequences: Vercel's timeout caps the run; mobile browsers killing a backgrounded tab abort the fetch and strand the user (work continues server-side but the client never redirects to results); the progress UI is fabricated — `styles/page.tsx:160` hardcodes `progress={30}`, and preview progress is a timer simulation (`src/hooks/use-generation.ts:61-74`). The irony: a real DB-backed progress function exists and is dead code (`pack.service.ts:436-460`, zero callers).

**F11 — Three component roots, two source roots. (Low)**
`components/ui/`, `app/components/`, `src/components/` coexist; pages live in `app/` while logic lives in `src/`. *[judgment]* Tolerable, but every new file forces a "where does this go?" decision; consolidation is cheap during M3.

### 3.4 Code quality & dead code

**F12 — Lint: 43 errors, 47 warnings; typecheck: 3 errors. (Medium)**
`bun run lint` fails (run verified). Notables: `react/no-unescaped-entities` errors, `prefer-const` error in `image-processing.service.ts:59`, `set-state-in-effect` warnings, and ~6 `no-img-element` warnings in results/styles components (`sticker-thumbnail.tsx:42`, `sticker-modal.tsx:108`, `style-preview-card.tsx:67`) — raw `<img>` for sticker grids is a real mobile-bandwidth cost, not just style nits.

**F13 — Dead code. (Low)**
`src/lib/services/session-cleanup.ts` (`cleanupExpiredSessions`) has zero callers and no cron — so the advertised 24h session expiry/cleanup never actually runs (also feeds F7). `generateMultiplePacks` (`pack.service.ts:489-523`) and `getGenerationProgress` (`pack.service.ts:436-460`) have zero callers outside their own file (verified by grep).

### 3.5 Dependencies & repo hygiene

**F14 — Dual lockfiles. (Medium)**
Both `bun.lock` and `package-lock.json` are tracked. AGENTS.md declares Bun. Mixed installs produce divergent dependency trees between machines/CI.

**F15 — ~40MB tracked; ~300 files of unrelated projects. (Medium)**

### 3.8 UX (the "decision fatigue" + mobile ask)

*[judgment, grounded in the cited code]*

All optional, but they read as a form to fill. The CTA itself ("Generate 5 Style Previews", `page.tsx:222`) leads with mechanics, not outcome.

## 4. Improvement Strategy (Phase 3)

### Theme A — Stabilize `main` before anything else
Most findings trace to one root cause: **five branches merged without a gate**. Target state: every push runs install → lint → typecheck → unit tests → build in CI; `main` is always deployable. Principle: a safety net is cheaper than any single bug it catches.

### Theme B — Models are data; routing is mechanism (the user's ask #1)
Replace the two-branch dispatch with a **model registry**: each model is a declarative entry `{ id, adapter, endpoint/model-name, capabilities (ref-image, transparency, sizes), promptStyle }`, and one env var (`IMAGE_MODEL=nano-banana-pro | gpt-image | flux-2-pro | nano-banana-2`) selects the default, with the existing fallback chain ordered by registry priority. Adapters shrink to pure transport (fal HTTP, BFL HTTP, OpenAI Images HTTP); sticker-prompt policy moves up to `prompt.service` where it belongs (fixes the F9 leak). Adding a model becomes one registry entry. Direct-REST adapters fit the existing culture (no SDKs used today); the Vercel AI Gateway is a credible alternative that would collapse all adapters into one — noted as an open question, not prescribed.

### Theme C — Generation is a job, not a request (user's ask #2's real blocker)
Target: `POST /api/generate/packs` validates, reserves credits, kicks off work, and returns `202 { generationId }` immediately; the client navigates to results and polls real progress (the schema and the dead `getGenerationProgress` already support this). Refresh-safe, sleep-safe, honest progress. Same pattern later for previews. Principle: the browser observes work; it must not own it.

### Theme D — Money paths are transactional
Atomic credit ops as Postgres functions (`deduct_credits(user_id, n)` with a balance guard, `add_credits`), webhook grants credits *before* marking completed (or in one RPC), reserve-then-refund around generation. Principle: read-modify-write is forbidden where money is involved.

### Theme E — Default-first UX (user's ask #2)
One decision above the fold: the photo. Language defaults from `navigator.language`; style/context collapse into an "Add details (optional)" disclosure; CTA becomes outcome-first ("Make my stickers"). Restore upload state from the server session on mount. Fix selfie-fidelity (F3) so the delivered packs match the promise users clicked for.

### Explicitly NOT fixing (and why)
- **Remotion side-projects' internals** — move them out (M3), never refactor them here.
- **Git history rewrite** to purge the 15MB media — not worth the disruption for a small-team repo; just stop tracking going forward.
- **Replacing Legend State / state-management churn** — it works; churn has no user payoff.
- **E2E in CI** — needs live keys and a seeded Supabase; keep e2e manual until the unit+build gate has been green for a while.
- **eslint 10 / TypeScript 6 major bumps** — defer; zero product value now.
- **IP-based rate limiting** — log and watch first; build it when abuse is observed or before paid acquisition (open question #4).

### Definition of done (measurable)
1. CI green on `main`: build + tsc + lint + vitest all pass; branch protection requires it.
2. `IMAGE_MODEL=gpt-image` (or `nano-banana-pro`) switches the default model with **zero code changes**; both new models generate a pack end-to-end.
3. A pack generation survives page refresh and phone sleep; progress shown = stickers in DB.
4. Concurrency test: two parallel pack requests against a 1-credit account → exactly one succeeds; webhook replay grants credits exactly once.
5. Selfies are unreadable without a signed URL.
6. First-time mobile user reaches previews with ≤2 taps after photo selection.

### Implementation sketches (top 3)

**Sketch 1 — Model registry (2.1).**
```ts
// src/lib/ai/registry.ts
export interface ModelEntry {
  id: string                        // 'nano-banana-pro'
  adapter: 'fal' | 'bfl' | 'openai' // transport, not policy
  remoteModel: string               // 'fal-ai/nano-banana-pro', 'gpt-image-1.5', ...
  supportsReferenceImage: boolean
  supportsTransparency: boolean
  envKey: string                    // which API key gates availability
}
export const MODELS: ModelEntry[] = [ /* data, one line per model */ ]
```
- `provider.ts` keeps its public surface (`generateImage`, `generateImageWithFallback`, result types) but dispatches via `MODELS.find(m => m.id === modelId)` → `adapters[entry.adapter]`. Default = `process.env.IMAGE_MODEL` validated against the registry (fail noisily on unknown id); fallback order = registry order filtered by key availability.
- Move `buildStickerPrompt` out of `fal.ts:101-114` into `prompt.service.ts` so all models receive identical prompts.
- New `openai.ts` adapter: `POST /v1/images/generations` (and `/edits` when a reference image is supplied, since GPT Image takes reference via the edits endpoint); b64 response → existing `GenerateImageResult.imageBase64` path. Nano Banana Pro is just a registry row reusing the fal adapter.
- DB: widen `Provider` to `string` (`types/database.ts:4`) and store the model id; no migration needed if the column is already text.
- Gotchas: GPT Image needs `OPENAI_API_KEY` + org verification for some models; per-model size constraints differ (registry carries allowed sizes; `image-processing.service` already normalizes to LINE specs afterward, which absorbs most variance). Update `scripts/test-providers.ts` to iterate the registry.

**Sketch 2 — Async pack generation (2.2).**
- Route: validate + reserve credits (1.2) + create pack rows with `status: 'pending'`, then start work without awaiting — on Vercel use `import { after } from 'next/server'` (or `waitUntil`) so the function isn't tied to the response; return `202 { generationId }`. Keep `maxDuration = 300` on the route as the work still runs in that invocation.
- Client: `styles/page.tsx` navigates to results immediately; results page polls `GET /api/generations/[id]/progress` (revive `getGenerationProgress`, `pack.service.ts:436` — count stickers per pack from DB) every ~2.5s until `completed|failed`, rendering stickers incrementally as they appear.

## 7. Second-Pass Findings (2026-06-10)

A second audit pass covered the areas the first pass reviewed lightly: auth/session migration, Stripe checkout, sharing/gallery, the three SQL migrations (RLS), download/export routes, and client hooks. All findings below were verified by reading the cited code directly.

### [N1] Checkout swallows the purchase-record failure that the webhook depends on — **High, compounds F2**

- **Evidence:** `app/api/stripe/checkout/route.ts:118-121` — when the `purchases` insert fails, the code logs and continues with the comment "Don't block checkout — the webhook will still work." That comment is false: `app/api/stripe/webhook/route.ts:39-48` looks up the purchase by `stripe_session_id` and returns 404 "Purchase not found" when the row is missing — credits are never granted.
- **Impact:** A transient DB failure at checkout time means the customer pays and can never be automatically credited.
- **Effort:** S · **Risk:** LOW · **Confidence:** HIGH
- **Fix sketch:** Create the purchase row *before* creating the Stripe session (fail checkout loudly if it can't be written), and add a webhook fallback that reconstructs the purchase from the Stripe session's `metadata` (`user_id` and `credit_pack_id` are already set at `checkout/route.ts:100-103`). → Plan 002.

### [N2] Migration seeds placeholder Stripe price IDs — **Medium**

- **Evidence:** `supabase/migrations/20260316000001_credits_and_purchases.sql:50-53` — seeds `price_starter_placeholder`, `price_pro_placeholder`, `price_mega_placeholder`.
- **Impact:** Checkout against a freshly-migrated database fails at Stripe with an invalid-price error. Whether production rows were manually corrected is unverifiable from the repo.
- **Effort:** S · **Risk:** LOW · **Confidence:** HIGH (seed), MED (production impact)
- **Fix sketch:** Verification step + env-driven seed correction. → Plan 002, step 7.

### [N3] Anonymous→user session migration is non-transactional and mishandles multi-session users — **Medium**

- **Evidence:** `src/lib/services/auth.service.ts:55-84` — four sequential writes (move generations, move uploads, recount, delete session) with no transaction. `auth.service.ts:37-41` — `.single()` errors when a user has more than one session; the error is discarded, so the code falls into the "claim the anonymous session" branch and creates yet another user session.
- **Impact:** Partial failure orphans generations/uploads mid-merge; duplicate user sessions accumulate over time (the rest of the codebase assumes one, e.g. `session.service.ts:117-129` picks the most recent).
- **Effort:** M · **Risk:** MED · **Confidence:** HIGH
- **Fix sketch:** Move the merge into a single Postgres function (RPC), mirroring the credits RPC pattern. → Plan 007, step 6.

### [N4] Post-response work is fire-and-forget on serverless; view counts also race — **Low/Medium**

- **Evidence:** `app/packs/[slug]/page.tsx:49` — `incrementViewCount(pack.id)` is called unawaited in a server component; on Vercel the instance may suspend after the response, so the write may never execute. `src/lib/services/share.service.ts:161-177` — the increment itself is read-then-write.
- **Impact:** Undercounted/lost view counts (gallery sorts and social proof rely on them).
- **Effort:** S · **Risk:** LOW · **Confidence:** MED (runtime suspension), HIGH (race)
- **Fix sketch:** Wrap in `after()` from `next/server` and use an atomic SQL increment. → Plan 007, step 5.

### [N5] Pack-ownership parameter is named `userId` but receives a session ID — **Low (correct today, trap tomorrow)**

- **Evidence:** `src/lib/services/share.service.ts:33-54` — `publishPack(packId, userId)` compares `generation.session_id !== userId`; its caller passes the cookie session ID (`app/api/packs/[packId]/share/route.ts:24`). The same session-only ownership check is used in `app/api/packs/[packId]/download/route.ts:54` and the export routes.
- **Impact:** Any future caller passing a real user ID type-checks fine and silently breaks authorization. Side effect today: an authenticated user on a second device (different session cookie) gets 403 on packs they own.
- **Effort:** S · **Risk:** LOW · **Confidence:** HIGH
- **Fix sketch:** Rename the parameter to `sessionId`; extend ownership to "session matches OR `generation.user_id` = authenticated user." → Plan 007, step 4.

### [N6] Share slugs generated with `Math.random()` — **Low**

- **Evidence:** `src/lib/services/share.service.ts:21-27` — 8 chars of base-36 from a non-cryptographic PRNG.
- **Impact:** Marginal — packs are public-by-choice — but unlisted-URL semantics deserve a CSPRNG.
- **Effort:** S · **Risk:** LOW · **Confidence:** HIGH
- **Fix sketch:** `crypto.getRandomValues`. → Plan 007, step 5.

### [N7] N+1 in session history — **Low**

- **Evidence:** `app/api/session/route.ts:14-26` — one `getStylePreviewCount` query per generation inside `Promise.all`.
- **Impact:** Bounded (≤10 generations per session); ~10 extra queries per `/api/session` call.
- **Effort:** S · **Risk:** LOW · **Confidence:** HIGH
- **Fix sketch:** Single grouped count query. Bundled into Plan 006 (which extends this route anyway).

### Findings considered and rejected (do not re-audit)

- **Auth-callback open redirect via `next` param** (`app/(auth)/auth/callback/route.ts:7-12`): `next` is always concatenated after a full origin (`${origin}${next}` / `https://${forwardedHost}${next}`), so `//evil.com` becomes a path, not a host. Safe as written.
- **`x-forwarded-host` trust in the auth callback:** platform-set on Vercel; this is the standard Supabase SSR pattern. By design.
- **Webhook ignores `checkout.session.async_payment_succeeded`:** card payments are synchronous; async payment methods are not enabled. Out of scope for now.
- **RLS policies missing INSERT/DELETE:** all writes go through the service-role admin client by design (`supabase/migrations/20260316000000_auth_user_id_profiles_rls.sql:104-106` documents this). Not a gap.
- **Positive note:** ownership checks on download/export/results routes are present and correct for the session model (`download/route.ts:54`, `results/route.ts:93-106`).

**Target design (declarative).**

```ts
// src/lib/ai/registry.ts  — models are DATA. Adding a model = adding a row.
export type AdapterId = 'fal' | 'bfl' | 'openai'
export interface ModelEntry {
  id: string                 // public id used in IMAGE_MODEL and stored in generations.provider
  adapter: AdapterId
  remoteModel: string        // what the adapter sends to the API
  supportsReferenceImage: boolean
  envKey: 'FAL_API_KEY' | 'BFL_API_KEY' | 'OPENAI_API_KEY'
}
export const MODELS: ModelEntry[] = [
  { id: 'nano-banana-2',   adapter: 'fal',    remoteModel: 'fal-ai/nano-banana-2',   supportsReferenceImage: true, envKey: 'FAL_API_KEY' },
  { id: 'nano-banana-pro', adapter: 'fal',    remoteModel: 'fal-ai/nano-banana-pro', supportsReferenceImage: true, envKey: 'FAL_API_KEY' },
  { id: 'flux-2-pro',      adapter: 'bfl',    remoteModel: 'flux-2-pro',             supportsReferenceImage: true, envKey: 'BFL_API_KEY' },
  { id: 'gpt-image',       adapter: 'openai', remoteModel: 'gpt-image-1',            supportsReferenceImage: true, envKey: 'OPENAI_API_KEY' },
]
// Registry order = fallback priority. IMAGE_MODEL env picks the default; unknown id → throw at startup (fail noisily).
```
