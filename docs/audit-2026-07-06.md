# Pre-Ship Audit — 2026-07-06

Full-codebase review: API routes, services, migrations, AI adapters, client hooks/pages. Issues ordered by severity. Line references are approximate.

---

## P0 — Ship blockers

### 1. Nightly cron deletes paying users' data and kills public share links

`src/lib/services/session-cleanup.ts` deletes **every** session with `last_active_at` older than `SESSION_TTL_DAYS` (default 1 day) — there is no `user_id IS NULL` filter. Per the schema (`docs/specs.md`), `generations.session_id → sessions ON DELETE CASCADE`, and `sticker_packs`/`stickers` cascade from generations. So the 3am cron (`vercel.json`) cascades away:

- Logged-in users' entire generation history and packs (paid for with credits)
- Published packs: gallery entries and `/packs/{slug}` share links 404 permanently

**Repro:** Log in, buy credits, generate a pack, publish it. Don't visit for 25 hours. Cron runs → pack rows gone, share link dead, history empty.

**Fix:** In `cleanupExpiredSessions`, add `.is('user_id', null)`. Also exclude sessions that own public packs (or reparent packs before delete). Separately: this cleanup deletes DB rows but never removes storage objects — add storage cleanup or the buckets grow forever.

### 2. Logging in mid-flow orphans the session cookie

`merge_anonymous_session` (migration `20260610000001`) moves generations/uploads into the user's **existing** session and `DELETE`s the anonymous session — but nothing updates the `ai-stickies-session` cookie. `migrateAnonymousSession` discards the RPC's returned session id. `getOrCreateSession` only sets the cookie when it *creates* a session, not when it resolves one by `user_id`.

After login (for any user who has logged in before), the cookie points to a deleted session. Everything keyed on the cookie then fails: `POST /api/generate/packs` → `INVALID_SESSION` 401, uploads' `completeUpload` → 401, exports/downloads → 401/403.

**Repro:** As a returning user in a fresh browser: upload photo → generate previews (anonymous) → sign in when prompted → click Generate Packs → 401.

**Fix:** Have `/api/auth/migrate` read the RPC return value and re-set the session cookie to the merged session id. Also set the cookie in `getOrCreateSession`'s `getSessionByUserId` branch.

### 3. Failed/interrupted pack generation is unrecoverable and eats credits

`app/api/generate/packs/route.ts`:

- Credits are deducted, status set to `processing`, then the real work runs in `after()`. If the function is killed (deploy, `maxDuration` 300s exceeded — plausible: 5 packs × 10 stickers × up to 3 provider retries × model fallback), the generation is stuck at `processing` forever, credits are gone, and no refund runs.
- Retry is impossible by design: the route 409s if status is `processing` **or** if any `sticker_packs` rows exist. `pack.service` inserts the pack row *before* generating stickers, so even a fully failed run leaves rows that block retry.

**Repro:** Start pack generation, redeploy mid-run (or have a provider outage). Generation stays `processing`; user can never retry that generation; credits not refunded.

**Fix:** (a) Make the status transition conditional (`UPDATE ... WHERE status NOT IN ('processing')` returning the row) so it doubles as a lock. (b) Allow retry when status is `failed` (delete/reuse empty packs). (c) Add a reconciliation path for stale `processing` generations (e.g., results route marks generations processing > N minutes as failed and refunds).

### 4. Google sign-in breaks the header for users with avatars

`app/components/layout/auth-buttons.tsx` renders `next/image` with `user.user_metadata.avatar_url`. Google OAuth (enabled in `login/page.tsx`) sets avatars on `lh3.googleusercontent.com`, which is **not** in `next.config.ts` `remotePatterns` (only `*.supabase.co`). `next/image` throws on unconfigured hostnames → nearest error boundary (`app/error.tsx`) replaces the page.

**Repro:** Sign in with any Google account that has a profile photo. Every page with the header errors.

**Fix:** Add the host to `remotePatterns`, or use a plain `<img>` for avatars.

### 5. Stripe webhook grants credits for unpaid checkouts

`app/api/stripe/webhook/route.ts` completes the purchase on `checkout.session.completed` without checking `session.payment_status`. For delayed-notification payment methods, `completed` fires with `payment_status === 'unpaid'` — credits are granted before money arrives, and a later payment failure is never handled.

**Fix:** Grant only when `session.payment_status === 'paid'`; handle `checkout.session.async_payment_succeeded` / `async_payment_failed`. (The `complete_purchase` RPC's `FOR UPDATE` + status check makes double-delivery safe — that part is correct.)

## P1 — High

### 6. Concurrent pack requests double-charge and double-generate

In `POST /api/generate/packs`, the `status === 'processing'` check, the existing-packs check, and the status update are all check-then-act with no conditional guard. Two simultaneous requests (double-click, two tabs) both pass the checks, both `deductCredits`, both launch jobs.

**Repro:** Fire two POSTs to `/api/generate/packs` concurrently with the same body.
**Fix:** Same conditional-UPDATE lock as issue 3a.

### 7. Session rate limit is not atomic and charges for failures

`incrementGenerationCount` (`session.service.ts`) is read-modify-write, and `/api/generate/previews` runs `checkRateLimit` → then `Promise.all([generate, increment])`:

- N parallel requests all see `remaining > 0` and all proceed — the free-tier cap is bypassable.
- The increment fires in parallel with generation, so a **failed** generation still consumes one of the user's 10 free generations.

**Fix:** One RPC: `UPDATE sessions SET generation_count = generation_count + 1 WHERE id = $1 AND generation_count < max_generations RETURNING ...`; call it *before* generating and decrement on failure (or accept charge-on-attempt, but atomically).

### 8. Background pack job clobbers `generation_count`

`runPackGenerationJob` writes `generation_count: initialGenerationCount + results.length` — a value snapshotted up to 5 minutes earlier. Any preview generation the user runs while packs are generating gets overwritten (lost update), reopening free-tier quota.

**Fix:** Atomic increment (`generation_count = generation_count + N`) via RPC.

### 9. Auth model is inconsistent across routes — logged-in users on a new device are locked out of their own content

- `GET /api/packs/{id}/download` and `/export/{platform}` return 401 if there's no session **cookie**, before ever checking auth — an authenticated user without a cookie can't download their packs.
- `GET /api/session/download-all`, `GET /api/session/marketplace-export`, and `POST /api/packs/{id}/export` authorize **only** by `session_id` — no `user_id` fallback at all.
- `GET /api/generations/{id}/results` and `/api/session` resolve the user's *single most recent* session; generations attached to any older session 404 even though `generations.user_id` matches.

**Repro:** Log in on a second browser → open History → click any generation → results 404 / downloads 401.

**Fix:** One shared authorization helper: allow if `generation.user_id === auth user` OR `generation.session_id === cookie session`. Apply it to all seven content routes. Stop resolving "the user's session" — resolve the generation directly.

### 10. Anonymous upload flow creates sessions that ignore the logged-in user

`upload.service.ts` has its own `getOrCreateSessionContext` that never sets `user_id`, even when the caller is authenticated. A logged-in user whose cookie expired gets a fresh **anonymous** session on upload; their subsequent generations aren't attached to their account (until a later migrate call happens to fire). Consolidate with `session.service.getOrCreateSession`.

## P2 — Moderate

### 11. Share URLs hardcode a domain that doesn't match the rest of the app

`src/lib/utils/share.ts` hardcodes `https://aistickies.com`; ZIP READMEs and docs say `https://ai-stickies.app`. Copy-link, tweet/LINE/WhatsApp shares, and OG `url` metadata all point at whichever of these you *don't* actually deploy to. **Fix:** `NEXT_PUBLIC_APP_URL` env var, used everywhere.

### 12. Seeded Stripe price IDs are placeholders

Migration `20260316000001` seeds `credit_packs` with `price_starter_placeholder` etc. On a fresh production DB, checkout 500s at `stripe.checkout.sessions.create`. Ensure the deploy runbook includes `scripts/verify-stripe-prices.ts` / updating those rows, or gate `is_active` on real price IDs.

### 13. Unpublishing a pack doesn't actually make images private

Stickers live in the **public** `stickers` bucket. `unpublishPack` flips `is_public`, which kills the `/packs/{slug}` page, but every sticker image URL that was ever shared remains publicly fetchable forever. Same for selfie-derived style previews (`{sessionId}/previews/...` in the public bucket). Given the source material is people's faces, consider signed URLs for previews and documenting that unpublish ≠ takedown (or move to a private bucket + signed URLs).

### 14. Post-checkout UX is silent

`/pricing?success=true` renders nothing different — no confirmation, and the balance shown may still be stale (webhook race). `CreditsBadge` fetches once on mount and never refreshes after purchase or pack generation. Add a success banner + re-fetch on window focus or after checkout return.

### 15. `AUTH_REQUIRED` on pack generation is a dead end

`create/styles/page.tsx` renders the 401 message as a full-page error with only "Back to Create" — losing the user's style selection at the exact moment you want them to convert. Detect `AUTH_REQUIRED` and route to `/login?next=/create/styles?generationId=...`.

## P3 — Minor

16. **Results page 'failed' state:** headline still reads "Your Sticker Packs Are Ready" when `status === 'failed'` (only the small eyebrow label changes).
17. **Provider errors leak to clients:** `/api/generate/previews` returns raw `error.message` (provider/API text) in 500 responses.
18. **`use-session.decrementGenerations`** syncs the Legend State observable from a stale closure (`state.remainingGenerations`) instead of the computed value.
19. **Upload metadata is client-declared:** the bucket enforces size/MIME (good), but `uploads.size_bytes`/`mime_type` record whatever the client claims.
20. **Partial packs cost a full credit:** a pack that produced 1/10 stickers still counts as a "result" and isn't refunded. Decide the policy deliberately.
21. **Retry amplification:** per-sticker retry (×2) × `generateWithRetry` (×3, incl. backoff) × model fallback (×N models) — a provider outage turns one pack into ~60+ upstream calls and multi-minute hangs. Cap total attempts per sticker.
22. **`compressToSize`** loops `quality` 100→10, but sharp's PNG `quality` implies palette quantization — verify visual output for stickers with soft edges, since this silently changes rendering style at the size boundary.
